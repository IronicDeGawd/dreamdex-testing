## Lessons (durable findings — preserved across rounds)
- **A rejection is not a verdict — scan the chain for existence proofs before declaring "unsupported" (2026-07-14, user-corrected).** Concluded 7702 "not supported" from 3 rejected probes + an ambiguous error; user pushed back → docs said supported → a 5000-block scan found 7 live type-4 txs (from a contest rival!) → mimicking their shape isolated the real rule (Somnia type-4 needs ~1.2M+ intrinsic gas; low limits get `invalid transaction`, not `intrinsic gas too low`). Rule: before declaring a chain feature absent, (1) read the chain's own docs, (2) scan recent blocks for anyone using it, (3) diff your tx against a real working one.
- **Unpushed branches nearly lost 2 days of work (2026-07-13).** `~/Project/Somniaforge` was deleted mid-session (cause unconfirmed) and restored from a 2-day-old snapshot; no Trash copy, no APFS snapshots, Time Machine unmountable. Only the server's deployed working tree + in-context session knowledge made full recovery possible — git history itself was unrecoverable. **Rule: push feature branches to the private origin after every deploy-worthy milestone; local-only git history is a single point of failure.**
- **R4 scoring correction (2026-07-13, from user).** R4 milestones count RAW volume — the R3 "effective volume × PnL multiplier" formula does NOT apply. The wrong carry-over briefly skewed strategy math (made the 1M milestone look unreachable). **Rule: when a new round starts, re-verify every scoring assumption against the round's own rules; never inherit a formula from the previous round without confirmation.**
- **Order-locked funds, instances 4+5 in one day (2026-07-13).** Engine-side (maker bleed guard, fixed via own tracked order state) AND control-side (/cohort recompute, fixed via account-keyed get_open_orders API). Any balance-derived metric must state where locked funds come from: engines use their own order state; control uses the open-orders API (it can see the engine's orders — same wallet).
- **R4 ERC-20 approve is absolute, not additive — always check on-chain allowance first (2026-07-12).** Two failures in one day: gas limit revert (InsufficientGasForPayout, fixed a13c721) and allowance revert (ERC20InsufficientAllowance, fixed a05df9a). The second: engine re-approved the pool before EVERY order for the API's mid-notional suggestion (~$70). ERC-20 `approve(spender, amount)` REPLACES the allowance (not adds), so each re-approve overwrote the startup pre-approve (500k USDso) down to ~$70. The pool pulls collateral at the LIMIT price (worst case, slightly above mid), and a small market tick pushed the pull to 69.95 USDso while allowance was only 69.95 → boundary revert. On-chain proof: WBTC→USDso allowance 69.95 (overwritten every order), WETH→USDso still 499,159 (WETH rarely traded so pre-approve never overwrote). **Rule: before approving, read current on-chain allowance and skip if it already covers worst case (2× price × qty); when approve IS needed, size to max(api_amount, worst-case-with-2x-margin), not the thin API amount.** Preserves startup pre-approve across many orders, avoids razor-thin edge cases.
- **Two distinct failures can share the same symptom — don't assume a repeat stop has the same root cause (2026-07-12).** Engine self-stopped 5-consecutive-failures twice in one day with different roots: first InsufficientGasForPayout (a13c721, gas-limit revert), second ERC20InsufficientAllowance (a05df9a, allowance revert). Both presented as "5 failures, halt trading"; identical symptom. Each fix required re-checking the actual on-chain revert selector, not replaying the prior fix. **Rule: capture the revert reason from the mined tx (or eth_call sim if pre-flight) and verify it matches the expected error before rushing to redeploy a past fix.**
- **R4 eth_call honesty — sim and broadcast must use the SAME gas limit (2026-07-12).** Diagnosed recurring "WETH BUY reverted" crashes: eth_call sim passed, mined tx reverted with InsufficientGasForPayout (0x782b2567), guard fires when `gasLeft < headroom` (payout needs ~1.7M for sweep, guard needs reserve). Broadcast used 3M limit → 3M − 1.7M = 1.3M left → guard aborts. Eth_call sim used node's ~50M default → 50M − 1.7M = 48.3M left → guard passes → mismatch. Fix: simulate_order_tx() now runs eth_call at the SAME 5M limit as broadcast (send_unsigned_tx); dishonest sim is worse than no sim (gives false confidence on code that fails live). Raised both limits to 5M. **Lesson: every parameter that affects bytecode execution (gas limit, chain ID, message value, sender nonce) must be identical between sim and broadcast or the sim is a lie.** gasUsed is cheap info; truthfulness requires matching the bottleneck.
- **R4 true capital = free + reserved + inventory (2026-07-10).** THIRD occurrence of same class of bug: value that LEFT the wallet is NOT value that is LOST. Wallet-USDso-only readings misreport capital whenever value sits in (a) base inventory held mid-round-trip, (b) quote reserved in a pool by an unfilled order, (c) the leaderboard's inventory-blind PnL. Engine measured only wallet USDso, misread $100 "bleed" from a $101.59 unfilled BUY reservation, tripped $30 cap, self-stopped a healthy 776-trip run ($123,727 volume, $13.27 real bleed = $0.107/1k, our best rate). Fix: vault_usdso() reads `getWithdrawableBalance(user, USDso)` per pair, usdso_total() = wallet + reserved-in-pool. Every guard, cap, and metric must measure TRUE CAPITAL = free + reserved + inventory-at-mid. On restart, reorder loop: sweep stray bags BEFORE capital checks (they unlock value); skip bleed check while holding base inventory (it hides value from a USDso-only read). Verified live: engine trades clean, bleed negative after fix.
- **R4 cost gating: deterministic book vs noisy realized (2026-07-09):** Pre-trade implied toll (book effective spread × 5) has 1/5 the variance of realized rolling cost over 15-trip windows (stdev 0.045 vs 0.234/1k). Implied is drift-free and known before capital commits; realized is dominated by inventory price drift during ~30–60s hold, averaging out only over many trips. A $0.15 ceiling on noisy realized (stderr ~0.06) crossed randomly, pausing when book was cheap. Gating on DETERMINISTIC implied toll (computed fresh each trade from the book) + demoting realized to a slow safety breaker (window 50, fires 2× implied ceiling) recovers selectivity: engine now picks cheap moments instead of throttling to noise. LESSON: never throttle on a noisy realized estimator when a deterministic pre-trade predictor exists.
- **R4 leg size vs toll — WBTC market-impact floor is ZERO (2026-07-09):** Measured 54 trips across WBTC + WETH. WBTC touch ~$3.9M (>120 legs), toll flat 0.117–0.119/1k across $10–$120 legs; gas amortises (0.142/1k at leg $10 → 0.118 at leg $120). Halving leg to $60 would INCREASE total cost (gas doubles to ~3% while spread shrinks only ~20%, net +$0.02/1k). WETH tighter quoted but effective 0.0322% (touch ~$51, book-walk). ZERO impact in WBTC means pair choice now drives toll far more than leg size. Joint (pair, leg) optimization future work; for now, leg $80 is stable for WBTC.
- **R4 effective-spread selection & leg/pair interaction (2026-07-09):** Quoted top-of-book spreads understate the cost of pairs with shallow touches (book-walk). At $80 leg, WETH quoted tighter (0.0172%) but filled effective 0.0322% (touch ~$51), while WBTC quoted/effective both 0.0235% (touch ~$3.2M). Engine now walks 8 levels, computes VWAP for the leg size, ranks on effective spread, gates on effective, skips pairs whose depth < leg, falls back to top-of-book on endpoint failure. DEEPER: effective toll ∝ leg size. Same moment, leg $80→WBTC $0.117/1k; leg $40→WETH $0.093/1k; leg $120→higher spread-walk cost. Gas ~3% of cost. Optimization: halving leg doubles gas cost (~$0.004→$0.008/1k) but cuts spread ~20% → future joint (pair, leg) search could save ~$0.02/1k across a full round. (See context/plan/ for leg-tuning experiment design.)
- **R4 leaderboard metrics audit (2026-07-09):** When a round's scoring rule or ranking metric changes, audit EVERY place the old metric is used — not just the scoring formula. The dashboard's leaderboard re-sort logic (control/monitor) was carried over from R1 (tx-count KPI) and silently misreported our position by 3 places until the real-time standings diverged visibly (we saw #6, real was #3). Places to check: ranking/gating logic, sorting for display, thresholds used in decision logic, and any rollups/aggregates that assume the old metric. A tx-count vs volume sort is a big difference; smaller metric shifts (e.g. raw vs effective) can hide just as well.
- **R4 leaderboard PnL unreliability (2026-07-09):** Leaderboard `usdsoBalance − 150` PnL field EXCLUDES base tokens held mid-round-trip (WBTC, WETH inventory). So a trader mid-trade reads far worse than reality. Observed: trader-6 PnL −42.12 → −122.09, trader-5 −45.19 → −136.60 within minutes (phase snapshots, not real losses). - **R4 dynamic pair rotation (2026-07-08):**

- **R4 audit fixes — regression + convergence (2026-07-08):**
  1. **Dust / minQuantity regression:** snap_lot→floor rework sized the sell off the TRIP DELTA (qty bought), ignoring accumulated sub-minQ dust. WBTC has minQuantity=0.0001 (10 lots), so a fee-shave residual (e.g. 0.00007 from a partial fill or slippage) below that couldn't be sold independently and piled up over many trips ($3.10 trapped, read as $4.33/1k "bleed"). - **R4 key file format (2026-07-07):** `~/secrets/wallet_new_event.txt` stores private key as bare 64-hex WITHOUT 0x prefix on a "private key:" line (address on next line). Extract with `grep -oE "[0-9a-fA-F]{64}"` + prepend 0x; a 0x-anchored regex returns empty, yields "0 bytes" eth_account error.
- **pkill pattern self-matching in remote SSH (2026-07-08):** a pkill invoked as part of an SSH launch command (e.g. `ssh host "pkill -f control.app:app && python -m uvicorn control.app:app"`) can SELF-MATCH the pattern in its own cmdline if the command string is in the shell's process list. Result: pkill kills its own session before the launch runs → instant ssh exit 255. Fix: use a pattern absent from the launch command (e.g. match only an old process ID or a service name never in the cmdline), or rely on a lockfile/port-check instead of pkill, or launch in a detached session (nohup/screen/systemd).
- **Dep install idempotence for flaky networks (2026-07-08):** a startup script that reinstalls deps on every run (`pip install -r requirements.txt` each time) couples network reliability to process startup. On a flaky network, a transient pip timeout aborts the whole launch. Fix: make install idempotent by checking for a marker file (e.g. `if [ ! -f .deps-installed ]; then pip install ...; touch .deps-installed; fi`) or detecting the key binary already present (`command -v uvicorn` or `python -c "import uvicorn"`), so startup skips install if deps are cached and only re-runs on explicit rebuild.
- **R4 resilience — network outage survival (2026-07-09):**
  1. **Docker health-check state and startup race:** `docker inspect -f {{.State.Running}}` reports false for a container still in status=created (booting) — the watchdog saw a healthy just-launched engine as dead and rm+relaunched it. Use `{{.State.Status}}` and accept running/created/restarting/paused, plus a startup grace (3 min) to let the container fully initialize.
  2. **Watchdog must distinguish unexpected death from intentional stop.** The engine prints "=== STOP: <reason> ===" on every self-stop (target reached, bleed limit, gas refusal, breaker hit, explicit abort) and "ABORT" on startup refusal (market param refresh fail). Absence of those lines is the only safe restart signal. Deliberate /stop via API additionally clears an autorestart flag to refuse relaunches.
  3. **Transport errors must never share a failure counter with trade errors.** A single DNS outage classified as a trade failure hit MAX_CONSEC_FAIL=5 and halted a healthy run. Fix: wrap RPC calls to classify errors as TRANSIENT (DNS, timeout, connection) vs TRADE (revert, invalid, quote), backoff transients 30s→15m and retry forever, only increment trade-error counter on TRADE failures.
